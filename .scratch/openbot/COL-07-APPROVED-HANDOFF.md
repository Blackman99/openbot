## Original five acceptance criteria, unchanged

1. Cancelling a queued Task prevents any provider call for it.
2. Cancelling a running Task aborts the provider request and cancels every unfinished descendant.
3. Repeated cancellation leaves the Task tree in one consistent cancelled state.
4. Existing streamed output remains visible and marked interrupted.
5. Results arriving after cancellation cannot write or replace the final answer.

The authorization roles, expected-Run precondition, receipt shape, partial-output storage, abort cadence and structural columns below are recommended implementation decisions supporting these AC. They are not extra acceptance criteria already approved by the user. Preserve the original non-goals: provider refunds, pause/resume, and automatic retry of cancelled work. Do not implement delegation, handoff, recovery, new budget/slot policy or public `/v1` cancellation here. A browser SSE disconnect continues to cancel only its reader, never the Task.

## Recommended authority and command contract

Cancellation is permission to stop work, not permission to execute using someone else's model. Use fresh `ConversationTransaction.lock(..., 'inspect')` for the actual cancelling human, then require the policy below. Do not call `admitTaskTarget`, `GroupBotTransaction.executionTarget`, or provider admission to authorize stopping. No credentials are opened for cancellation.

| Caller                                                 | Recommended permission                                                                                                                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Original execution human                               | May cancel their selected Task/subtree while retaining current conversation inspection. In a group this means current workspace and group membership.                                    |
| Current group owner/admin                              | May cancel a Task/subtree in that group, including one whose original human has since left. Attribute the cancellation audit to this real moderator; keep `execution_user_id` unchanged. |
| Other group member                                     | May inspect permitted history, but cannot cancel another human's Task.                                                                                                                   |
| Workspace admin, Bot owner/inviter, or future Bot Lead | No implicit cancellation power over another human's private thread or a group they cannot currently moderate.                                                                            |
| Removed/deprovisioned caller                           | Denied, including receipt replay after a membership/role change.                                                                                                                         |

A closed/replaced group-Bot grant, an archived/deleted Bot, or unavailable/revoked provider must not prevent a still-authorized group human from stopping work. A direct thread keeps existing creator privacy and current **inspect** policy; do not quietly grant direct-thread access after its ACL has been removed. Archived/direct retained history already permits inspection where the current ACL allows it. Group cancellation needs no direct Bot ACL for the cancelling member/moderator.

Proposed private route: `POST /api/v1/workspaces/:workspaceId/conversations/:conversationId/tasks/:taskId/cancellations`, exact body `{idempotencyKey, expectedRunId}`. Follow COL-09's visible-ASCII 1–128 key and canonical UUID rules, trusted Origin, current session, strict fields and private/no-store responses. Public `/v1` remains API-04's work.

Return **200 after commit**: `{task, receipt:{commandId,taskId,rootTaskId,runId,attempt,cancelledAt,affectedTaskCount,affectedRunCount}}`. `task` is the current bounded COL-09 view; `receipt` is the immutable result recorded for this command. Do not return an unbounded descendant array or partial bodies with the receipt. This acknowledges durable cancellation, not that a remote provider has refunded or ceased every internal computation.

- Scope command uniqueness by `(task_id, actor_user_id, idempotency_key)` in a cancellation-specific table. Same key + exact expected Run returns the original receipt after fresh stop authorization; a changed payload returns 409 `idempotency_conflict` before any mutation. Do not rebuild the original counts/time from today's tree.
- A new cancellation requires the selected current Run to equal `expectedRunId`; otherwise return 409 `task_cancel_run_conflict`. This prevents an old tab from cancelling a newly retried attempt. On a new command, queued/running cancel; completed/failed return 409 `task_cancel_state_conflict` and leave their history/output untouched.
- Already-cancelled current Run + matching expected Run is a successful no-op. A distinct new key can store its own stable no-op command receipt with zero affected counts and the existing Run's cancellation time; it creates no second transition, Run, domain cancellation audit or SSE status event. Same-key replay creates nothing at all.
- Missing/inaccessible resources keep safe 403 `task_forbidden`; malformed input and unavailable errors reuse current Task envelopes. Only an actual 401 clears the Web session. Retry/cancel conflicts require deliberate refresh; an unknown transport outcome retains the unchanged key and expected Run for replay.
- A viewer-specific `permissions.canCancel` hint may be added to the bounded Task DTO/page under the same inspection policy. Treat it as display information; the command always rechecks. Do not derive moderation rights from a Bot label or expose membership internals.

## Atomic subtree transition and lock order

Add immutable structural identity now: `tasks.root_task_id`, nullable `parent_task_id`, and integer `depth`. Backfill existing Tasks as `(self, null, 0)`. A child must share workspace, conversation/group, root and original execution human with its parent; depth is parent depth + 1. Root has self root ID, null parent and depth 0. Cross-group/direct-thread delegation remains disallowed. Parent links never change, and strict increasing depth plus same-root guards prevent cycles. The public submit path still creates only roots. This supports meaningful multi-level cancellation fixtures without implementing a delegate action.

COL-14 will later own actual child creation, delegated trigger provenance, inherited budgets and target admission. The current human-trigger uniqueness/admission guards must not be bypassed merely to make a child fixture easy. Use explicit valid fixture construction under the test migration role; no public reparenting or fake delegation API. Existing root, parent and depth are structural fields, not a claim that the future delegate ticket is implemented.

The common ordering remains a subsequence of **workspace → group when present → Bot when required → conversation → root Task → remaining Task rows → current Run rows → cancellation/checkpoint records → provider only for execution**. Within a class, lock stable UUID order; always lock the root before any non-root Task. For one subtree mutation, acquire all affected Task rows before their Run rows. Cancellation has no provider locks and does not acquire descendant Bot locks after locking the conversation. The current workspace lock already serializes conforming workspace mutations; do not add a second global/advisory lock or remove that protection here.

One caller-owned transaction:

1. Validate IDs/input. Discover the persisted immutable scope, then take current conversation inspection and stop authorization. Lock the root and selected Task. Resolve same-key receipt before applying a new state transition, preserving authorization on replay.
2. Under the shared workspace/group/conversation/root locks, enumerate the entire selected subtree using the parent relation. Traverse through terminal intermediate nodes; filter only the mutation targets to current queued/running Tasks/Runs. Siblings and unrelated roots in the same conversation are excluded. Current topology is stable because every future child writer must hold these locks before insertion.
3. Lock the affected Task and latest Run rows deterministically. Verify the selected expected Run, each latest-attempt relationship and the ancestry again. Never cancel an old historical Run merely because it belongs to an affected Task.
4. Insert the immutable cancellation command/result and per-Run cancellation markers. Transition each affected current Run to `cancelled`, then its Task to `cancelled`; use one sampled cancellation time after lock waits. Preserve start time, claim, deadline, provider/model and already recorded usage. Queued cancellation keeps those unstarted fields null. Keep error null and final output null: cancellation is not a fabricated provider failure or a final Bot answer.
5. Freeze each already-published durable partial checkpoint. Insert safe mandatory cancellation audits attributed to the real actor, and typed `appendCancelledRunState` events through the existing conversation sequence. No-op/replay adds no transition event. Commit receipt, all Run/Task states, output freeze, audits and delivery records together; audit or allocation failure rolls everything back.

Do not commit descendants in batches or truncate the subtree to a page limit. Use database recursion and bounded internal iteration if needed, with one transaction and a small result receipt; later COL-12/COL-14 impose business depth/fan-out limits. A database timeout means rollback/unavailable, not a successful partially cancelled tree.

Every claim, delta, finish, retry and future child/handoff writer must acquire the same root lock and reject a cancelled ancestor before admitting new work. Check ancestors of the selected subtree as well as its own status. Particularly, a previously failed descendant stays failed (its immutable history is preserved), but its retry must fail after ancestor cancellation. Do not implement that by rewriting the failed Run to cancelled. COL-09 exact-key retry replay may still report its original immutable receipt/current Task after its normal authorization; it cannot create a new Run beneath cancellation.

| Race winner                                                | Required result                                                                                                                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cancel commits while Run is queued, before claim admission | Claim sees cancelled and invokes no provider. This is AC1's precise linearization.                                                                                              |
| Claim commits first                                        | The Run is already running; cancellation commits its durable stop state and the worker aborts its request. Do not promise atomic database commit plus remote network admission. |
| Delta commits before cancellation                          | Its bytes are in the checkpoint and retained as interrupted.                                                                                                                    |
| Cancellation commits before a waiting delta or finish      | Delta/finish returns a fenced result; no new text, usage overwrite, final ledger output, completion or failure transition can escape.                                           |
| Completion commits before cancellation                     | New cancel returns state conflict; the one existing answer remains unchanged.                                                                                                   |
| Child creation/retry wins first                            | A queued/running descendant is included in the same cancellation traversal. If cancellation wins first, the writer rejects before creating an attempt/child.                    |

## Durable partial output, independent of 0019 retention

Do not retain the whole SSE feed forever or assume its 24h/10,000-event/16MiB suffix contains an active Run's original prefix. `task_run_streams.delivered_bytes` is already durable, but stores no text. Also do not wait for the worker's cancellation callback to supply text: the API process cannot read that worker's memory, and it may be silent or die.

Recommended storage: one `task_run_partial_outputs` row per streaming Run, containing a bounded cumulative UTF-8 body, end byte and update time, keyed by Run. The row is a current output checkpoint, not permanent copies of every superseded rendering delta. For every accepted callback delta, append the normalized text to this checkpoint **in the same transaction** as `appendAssistantDelta`, advance it to exactly `task_run_streams.delivered_bytes`, and do this before retention can reclaim that delta. Retain the existing 32,000-character/128,000-byte output limits and exact contiguous UTF-8 offsets. Never replay `response.events` into this writer.

While the current Run is running, the checkpoint may only extend its exact prefix with the matching newly committed delta. After cancellation it is immutable and its `interrupted` meaning derives from the durable cancelled Run/marker. Pending process-local text that never committed as a delta was not streamed and is discarded; already committed text is never discarded on cancel. No partial creates a `bot.message.created` event, current-answer receipt, human edit/delete control, memory/context result, or successful completion.

On successful completion, the canonical ledger owns the answer. Delete the superseded checkpoint in the same accepted finish transaction through a narrowly guarded path that requires the completed Run's valid final output; deletion of cancelled checkpoints remains denied. Failed Run checkpoints may remain frozen as attempt evidence; COL-09 history stays immutable. Do not invent post-cancellation token counts from a late callback. Any usage not durably reported at the cancellation boundary remains unknown.

Proposed reader: `GET .../tasks/:taskId/runs/:runId/partial-output`, returning `{conversationId,taskId,runId,partial:null|{text,endByte,interrupted:true}}` for a cancelled Run, under current conversation inspection and exact Task/Run binding. Keep body and serialized-response limits explicit; a single maximum-size checkpoint fits the existing 1MiB Task JSON budget. Use a bounded detail fetch rather than embedding up to 50 maximum-size bodies in Task/history pages or every SSE state frame. A queued cancellation returns `partial:null`.

Keep the existing `task.run.updated` envelope and cursor; extend its status union/nullability with cancelled, without adding mandatory fields to old persisted version1 execution JSON. A cancelled event keeps the visible preview, marks it **Interrupted**, and resolves the durable checkpoint when necessary. On reload or 410 recovery, the current cancelled Run identifies the same authorized detail reader. The conversation view may keep its existing aggregate preview budget and explicit detail links; the Task detail/history view must expose the full stored partial. Do not enter a missing-preview reconnect loop, silently hide the content after terminal status, append a synthetic final answer, or resubmit the Task. Tests must cover the current reducer's terminal-preview deletion branch.

**Approved upgrade policy:** stop new claims and drain the old worker before migration0023. The migration must fail atomically when any pre-existing Run is still `running`; queued Runs remain durable and are handled by the new worker after upgrade. Do not guess, backfill or fabricate a prefix already lost under0019 retention. No old worker may continue publishing across this migration. The migration preflight, refused-upgrade rollback and preserved queue must have explicit native/Compose evidence before release.

## Independent worker abort

The worker needs a Run-scoped cancellation observer during the entire generate promise, including before the first callback and between indefinitely silent chunks. A process-local AbortController registry or SSE subscription is insufficient across separate API/worker processes.

Recommended default: a bounded database status check immediately before provider generation, then at most a **1,000 ms interval**, with only one in-flight check per active Run and the existing finite connection/query timeouts. Read persisted Task/Run/current-claim and cancellation state; these are worker metadata, not content admission. If no longer the current running uncancelled claim, abort that Run's controller. Keep the process shutdown signal and task deadline in the combined signal. The 1s is a detection target under a responsive database, not an unconditional network SLA.

On database observation failure, abort the local request rather than continue blindly; do not assert durable cancellation without a committed cancellation row. Let existing failure/loop handling report the bounded database failure; do not implement crash recovery here. Clean up the timer, listeners and in-flight observation in `finally` on all finish, error, timeout, cancellation and shutdown paths. Cancellation of one Run must not stop the worker loop or other Runs.

Use the existing abort-aware transport and preserve `withAbort`-style consumption of late promise outcomes. A deliberately non-cooperative test adapter may resolve after abort; it still cannot publish through `publishDelta`/`finish`. Distinguish a durable cancelled claim from `provider_failed`/`worker_stopped` in internal control flow so a late worker cleanup cannot replace cancelled with failed. Discard the pending publication buffer; any publication that committed before the cancel lock remains in the checkpoint, any waiting publication rechecks and loses.

## Legal multi-level fixture construction

The fixture first uses real authentication, workspace/group membership, Bot/grant admission and conversation APIs.
