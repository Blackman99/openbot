1. As a Bot editor, I want an explicit retry limit and ordered fallback choices, so execution follows the configuration I reviewed.
2. As the triggering human, I want temporary failures retried within that limit, so a brief outage does not require another prompt.
3. As the triggering human, I want authentication, invalid requests and lost access to stop automation, so execution does not switch models to bypass them.
4. As a conversation reader, I want waiting, failure and model-switch evidence for every attempt, so I can understand the final answer's provenance.
5. As an authorized user, I want cancellation to stop pending follow-ups and manual retry confirmation to retain its original command, so uncertain responses do not create extra work.

## Existing facts and required additions

- Bot versions currently contain one `{scope, connectionId, modelId}` binding and four limits only: tokens 32,768 (1–1,000,000), duration 300s (1–3,600), turns 8 (1–100), delegation depth 2 (0–8). No Bot retry/fallback fields exist. Configuration parsing, version edits/comparison/restore/copy, safe configuration mappers and strict Web/public DTOs all require coordinated allowlist changes; historical JSON must remain unchanged.
- `ModelFailure` already has `code: string` and `retryable/non_retryable/unsupported_capability`; the worker discards these into `provider_failed`. Carry a validated closed failure code/class through the worker's internal finish outcome and persist safe provenance before adding scheduling. Do not infer transient status from the coarse Task error.
- Existing normalization is too broad for automatic action: all HTTP >=500 become `provider_unavailable`, Chat SSE maps an unrecognized error to `provider_interrupted_stream`, and transport drops individual connection-error reasons into `provider_unreachable`. Tighten these paths first: unknown/validation/TLS-certificate failures must not become transient through a generic category, including HTTP 200 SSE. Transport does not expose `Retry-After`; the first policy should not pretend to honor it.
- PROV-05 stores a mutable, same-scope connection graph (up to 16 direct edges) and computes a depth-first preview. It performs no runtime switch, retry or credential admission. Current durable admission enforces Basic and an exact model ID; it needs an explicit required-capability parameter before broader workloads can use the same seam.
- COL-09 supplies immutable consecutive Runs, stable manual retry receipts, current authorization, current-only TaskView plus complete paginated history, and old-claim fencing. It has no automatic scheduling, due-time column, episode counters or recovery lease. Its 0022 guards require a manual retry receipt for later Runs and require every claimed model to match the primary Bot binding; fallback cannot merely pass another connection to today's worker.

## Recommended policy and compatibility

- Add optional version configuration `retryPolicy: {maxAttemptsPerModel, maxRunsPerChain}` and `fallbackBindings: BotBinding[]`. Recommend per-model integer 1–3, default 1 (includes that model's first call), and chain integer 1–4, default 4, hard ceiling 4. Allow at most three distinct fallback connections, exclude the primary, and preserve explicit order. An absent legacy policy means per-model 1, no fallback and shared chain ceiling 4: ordinary provider failure still ends after its first attempt. Do not rewrite historical JSON or silently enable retries. New-Bot UI may explicitly recommend finite retries, requiring the saved version to carry that choice.
- One chain is the first Run of a user submission or the unique new Run committed by a fresh COL-09 manual retry. Persist `chainRootRunId`, `chainAttemptOrdinal` (1..effective cap), `previousRunId` and `origin: initial | manual_retry | provider_retry | model_fallback | worker_recovery`; the global Task `attempt` still increases across chains. Persist the chain limit snapshot and model ordinal. Every automatic reason consumes the same total; crash recovery additionally permits at most one new Run per chain. Same-key replay returns its original receipt without changing the current chain. A failed/rolled-back manual creation starts no chain. Automatic retry, fallback and recovery never reset either budget. Later hierarchical limits take the stricter bound and cannot increase this snapshot.
- The per-model cap gates COL-10 provider-failure retries; COL-11's separately authorized single crash recovery also advances the model ordinal and consumes the shared total, without renewing COL-10's allowance. Example with limits 3/4: primary Run 1 fails, provider retry Run 2 crashes, recovery Run 3 fails transiently, eligible fallback Run 4 is the last possible automatic attempt. Recovery retains the interrupted Run's already selected binding, including a fallback. A fresh manual retry starts at the original primary; no automatic path returns to an earlier model. The four-Run budget and these fields are new proposals, not existing capability.
- Retry only normalized rate limiting, temporary upstream unavailability, positively classified temporary network failure and genuinely interrupted transport. A local adapter deadline (`provider_timeout`) is always non-retryable, even while an outer Run deadline remains valid; this supersedes the earlier timeout recommendation. Recommend transient HTTP 429/500/502/503/504 and an Anthropic 529 only with its explicit `overloaded_error` envelope. Permanent or unknown structured errors override a coarse status. Do not classify 501/505, TLS validation, clean EOF without a terminal frame, semantic Responses `incomplete`, or arbitrary structured/network errors as transient. Authentication, request validation, unsupported capability, malformed response, URL-policy denial, permission loss, worker stop, cancellation, context/output limits and execution timeout get no automatic retry or fallback. Unknown means terminal. Local deadline/cancellation/publication failures take precedence over provider categories; an external abort also takes precedence over a coincident local adapter deadline.
- Persist a single `notBefore` at scheduling: first same-model retry after 1s, second after 2s, plus 0–250ms bounded jitter chosen once; entering a fallback waits 1s plus the same bounded jitter. Polling/reconstruction reads that value, never redraws it. Existing duration/token checks remain per Run; this ticket does not claim a new task-tree budget or exactly-once provider execution.
- The Bot version's explicit list is runtime authority. The connection graph may suggest choices during editing, but saving copies reviewed complete bindings into the new version. Do not traverse the live graph at execution or silently import descendants. Later graph/default-Lead/Bot-version edits cannot alter an accepted Task. All bindings stay in the primary's personal-owner scope or same workspace; no credential proxy or cross-workspace fallback. Changing a model ID requires an explicit new Bot version; credential rotation may advance the new Run's connection revision.
- Validate newly supplied/restored/copied bindings in the Bot mutation transaction with the editing actor's rights; execution separately uses the original triggering human. A primary rebind/copy must explicitly preserve compatible fallback configuration or expose its removal for review, never retain unchecked foreign bindings. Current Basic is the text-only Task requirement. Persist a server-derived workload requirement; a future Collaboration/vision workload must satisfy its actual requirement, including current probe/override generation, never a weaker user-selected preview tier. Do not implement those workloads here.

## Durable transition, authorization and visibility

- Introduce one narrow transaction-owned next-attempt admission/writer shared with COL-09 and the future COL-11, retaining distinct reason-specific receipts. Add immutable COL-10 continuation evidence with source/next Run, shared chain provenance, model position/ordinal, selected binding, normalized reason and due time. Unique source successor, next Run and chain ordinal constraints arbitrate all origins under the Task lock; COL-10 and COL-11 must not each allocate a successor. Initial/manual attempts use the primary. Database guards must recognize these bounded typed receipts and the chosen version-listed binding, still rejecting orphan Runs, terminal rewrites, mismatched scopes and arbitrary provider substitution. Use the next actual ordered migration after integration; retain published 0022.
- Finishing a transient failed claim, retaining its failure, selecting at most one continuation, advancing the same Task to queued, writing mandatory audits and publishing old-failed/new-queued states share one admitted transaction. Audit failure rolls the complete transition back. No eligible target leaves that same Task failed with a fixed safe exhaustion reason. No additional Task, trigger, route decision or human command is fabricated. Only a committed due queued Run can perform provider I/O; the polling loop is a wakeup mechanism, not the schedule.
- Keep workspace → group → Bot → conversation → Task/Run → provider ordering and the actual caller-owned connection. Recheck current workspace/group membership, exact old grant, grantor Bot authority, Bot lifecycle, actual human's selected-model rights and capabilities after waits and before claim/publication. A revoked/reinvited grant cannot revive the Task. Skip inaccessible fallback candidates without disclosing metadata; once a scheduled target fails fresh admission, fail closed rather than rerouting that Run. Split target/instruction admission from primary-only model admission deliberately; validate the persisted selected binding against the retained version and continuation receipt.
- Reuse COL-05's typed allocator and claim fencing; previews remain separate by Run and new byte offset zero. Failed partial text is not a permanent answer, new prompt or prefix for the next attempt. Preserve current edited/tombstoned source behavior and the original trigger horizon; re-admit memory sources. No new SSE namespace or generic trusted append bypass.
- Extend safe current/history and stream DTOs with attempt cause, predecessor, due time, automatic progress/limit and bounded transition evidence. Record canonical IDs internally; expose safe provider name/protocol/model snapshots without endpoint, credentials, headers or raw responses. The mandatory fallback event at successful claim names the previous persisted actual provider/model, next actually admitted provider/model and normalized reason; the waiting UI distinguishes a planned target from a model already called. Show retry waiting, fallback reason, all failed evidence and the one current answer; reuse COL-09 history/locator and unchanged-command confirmation. Actual 401 alone clears a valid session; 403 preserves identity.
