## 1. Exact source manifest and successful-Run enqueue — new

Extend the claim transaction after the queued→running CAS and before commit to persist an ordered, body-free manifest of **what this Run actually sends**. Ordinary nondeleted message inputs record message ID, creation event/sequence, exact selected version event, conversation/workspace, role and input position. Selected memories record their exact version, approval/lineage IDs, and source references alongside MEM-01/MEM-02 manifests. Pinned Bot instructions remain attributable to the Task's immutable Bot version. Record skipped/deleted items only if necessary for bounds; do not pretend they supplied text.

Use the existing original trigger creation-sequence horizon and current projection for the target conversation's ordinary/group-reference inputs, including edits/tombstones. Explicitly approved cross-scope memory uses its own source coordinates and approval, never a numeric comparison between different conversations' sequences. A new retry Run gets its own newly selected manifest; never copy an old Run's manifest or later-added memories. After the claim commits, no manifest expansion is allowed. At each delta and final publication, current source eligibility must still hold for the complete selected set. Preserve current authority, exact grants, model checks, deadlines, cancellation/ancestor fences, and the one shared delivery allocator.

Recommended added bounds: selected context retains the existing shared 1,000-item / 1 MiB budget and at most 100 memories across all scopes. Flatten conservative provenance into at most 2,048 distinct event/version/approval references and at most 1 MiB of serialized locator metadata; reject overflow with a safe `context_lineage_limit` before provider invocation. Retain ancestor memory-version/approval dependencies as well as terminal message locators. Do not recursively discover an unbounded graph at review time, truncate dependencies, or treat these references as proof of a fact's semantic correctness.

Every new successful Run inserts exactly one `memory_extraction_job` referencing Run, canonical output event, manifest version/digest and extractor version in the **same** completion transaction. Job insertion/audit failure rolls back output, state and deliveries; the last deadline sample remains after all mandatory writes. No job for failed, cancelled, interrupted, partial-only, or stale-claim publication. Later extraction failure does not undo a completed Run or call its model again.

Upgrade recommendation: drain pre-manifest running Runs before enabling the migration/worker release. Existing completed history is not silently backfilled from guessed context; historical extraction without a trustworthy manifest reports `lineage_unavailable`. Queued Runs may be claimed by the new code. A database completion guard should require the manifest and unique job on post-upgrade completion transitions, including raw runtime-role writes. Do not retrofit or renumber migration 0020; choose the actual new migration only after the merged chain is known.

## 2. Bounded local extractor and job recovery — new

Recommended v1 is a pure, deterministic `local-marked-lines-v1` function. Scan the canonical final output only, with its complete conservative Run lineage plus output event as dependencies. Recognize explicit single-line markers `Remember:`, `Preference:`, `Decision:`, `记住：`, `长期偏好：`, `约定：`, `决定：` and bullets immediately under `Memory candidates` / `候选记忆`. Strip the recognized marker; ignore fenced code, empty entries and incomplete multiline entries. Do not interpret output instructions as authorization. This deliberately produces zero candidates when no supported marker exists.

Recommended caps: input at most the current canonical output ceiling, further capped to 32,000 Unicode code points / 128 KiB UTF-8; each candidate 1–1,000 code points / 4 KiB; at most 10 distinct candidates. Oversize input or more than 10 otherwise valid distinct candidates fails the extraction atomically with `extraction_limit`; never silently discard eligible facts. Oversize individual entries also produce that bounded failure. Extraction is a suggestion mechanism, not factual verification. Store rule confidence 0.5 with `confidenceSource: 'local_rule'` and rule version; the approval form labels it as a default for human assessment and records the reviewer-confirmed confidence separately. No scoring threshold auto-approves anything.

An explicitly configured model-assisted extractor is an alternative for a later scoped change: it would need its own authorization, cost consent, strict bounded schema and source validation. It is not required, enabled, or counted as delivered by MEM-03; the default adds no provider request, external extraction service, credentials dependency, or infrastructure.

Use the existing worker deployment with a separate bounded local-job consumer that can run without provider secrets. Suggested job fields: `runId UNIQUE`, `status`, extractor/normalizer versions, `attemptCount`, `availableAt`, `claimToken`, `leaseExpiresAt`, `lastErrorCode`, timestamps. Suggested states: queued/running/completed/blocked/failed. One job at a time per consumer; default 1 s polling, DB-clock 15 s lease, 5 s processing deadline, at most 3 transient execution attempts with 1 s then 5 s backoff. These are new extraction-job controls, not the unimplemented COL-11 Task recovery lease.

Claim by atomic CAS, use database time, and validate token, unexpired lease and current source eligibility again at the final transaction. Read admitted source under locks, compute locally outside the transaction, then revalidate before atomically inserting candidates, audits and job completion. Expired ownership can never renew or commit. A crash/unknown commit is resolved from the durable job and fingerprints; a restarted worker does not reopen the Run or reinvoke its provider. Permission/source changes are safe blocked outcomes, not automatic transient retries. An explicit retry after restored permission uses the same job/Run, never clears decisions; unchanged completed-job replay returns its existing outcome. A permanently stale source version cannot be revived by retrying.

## 3. Candidate identity, revisions and decisions — new

Candidate identity is unique `(runId, normalizedFingerprint)`. Normalize with Unicode NFC, CRLF→LF, trimmed outer whitespace, and collapse each run of ASCII spaces/tabs to one space while retaining internal newlines. **Preserve case, punctuation, digits and meaningful identifier characters**; pin these exact rules in tests and do not use NFKC or case folding to merge `US`/`us` or different identifiers. SHA-256 indexes the normalized UTF-8 representation; verify equality on a fingerprint conflict rather than silently accepting a different body. Extractor version or proposed destination is not a new deduplication namespace.

Store original fingerprint/proposed scope, exact origin Task/Run/Bot version, source manifest identity, confidence and pending state. Default proposed scope is the origin group for a group Run, or the real origin Bot for a direct Run; a proposal grants nothing. Candidate text edits create candidate revisions with author/time and expected-revision CAS. Editing does not change the original dedup identity. Retain fingerprints and rejection metadata even if body cells are later purged. Re-extraction cannot overwrite human edits or turn approved/rejected back to pending; no candidate deletion/recreation shortcut.

Approve and reject lock the same candidate and allow exactly one terminal decision. Reject requires a stable command key + expected revision, writes a mandatory decision audit/receipt, and creates no memory. Approval additionally creates one approved memory/version/lineage/receipt in the same transaction. All mandatory writes succeed or none do. Keys are unique by workspace + actor + command domain; canonical payload hashes bind candidate/revision, reviewed body/confidence and selected destination. Same key/payload replay reauthorizes and returns the stable old receipt plus current safe state; changed payload is 409. A stale edit, approve/reject race, or expired preview never creates a second memory. There is no automatic approval endpoint, including a job-internal one.

## 4. Real destination scopes and reviewed content — new

Add an explicit immutable memory payload distinction: the new `source_reference` discriminant describes MEM-01's existing reference semantics and MEM-02's planned approved private reference; MEM-03 `approved_fact` stores the exact edited/reviewed text with immutable lineage and human confidence. These discriminants are not fields already present in MEM-01. Candidate revision is separate from approved memory version 1. Do not feed an edited fact through `projectCurrentMemory` and replace the edited text with the original message. Do not copy it into `group_memories` while claiming that table already supports other scopes.

Implement actual same-workspace group, Bot-private and Workspace storage/read/search/context admission; coordinate Bot-private branches with MEM-02. Pending/rejected candidates are absent structurally from those selectors. Source and scope filtering happens before search/LIMIT. Group memories require that exact group/current grant for Bot context. Bot-private selection derives the target from the real `Task.bot_id`, so another Bot gets zero private results even if its execution human can edit both Bots. Human group reads require current group content membership; Bot-private management reads retain MEM-02's current edit admission. Workspace fact list/search requires current workspace membership, while writes require the role below. Workspace context additionally requires the real Task's same workspace and current direct/exact-grant execution admission. No scope grants cross-workspace or original-source access, and all consume the combined memory/context budgets.

Recommended human authority:

| Operation / destination | Fresh authority in the same transaction |
| --- | --- |
| Review, edit, reject | Current source Run conversation inspection and current eligibility of the referenced content. Group content membership suffices; direct conversation remains creator-private with current inspect permission. No administrator bypass into a private conversation. |
| Group target | Source authority above plus current destination group content membership, following MEM-01's write policy. |
| Bot target | Source authority plus current destination Bot owner/editor permission and nondeleted lifecycle; pin expected Bot version. Archived targets may retain reviewed content but do not become executable. |
| Workspace target | Source authority plus current workspace owner/administrator role. |
| Another workspace | Rejected, even if the person belongs to both workspaces or checks a confirmation box. |

Local extraction acts for the stored execution human using current source inspection/content eligibility; unavailable provider credentials alone do not prohibit review. Direct-Bot Run support needs a new creator-private current-source adapter; the existing group-only `sourceForMemory` is not sufficient. Its proposed destination may be the originating Bot, but publishing to that Bot spreads content beyond the private conversation and therefore always requires the extra disclosure below.

For selected promoted/approved memory dependencies, use the existing approval's narrowly authorized **derived content**, not an implicit right to read every ancestor message. A reviewer can see only source details that their own current source admission permits. A destination-only reader receives the reviewed fact and safe attribution, never inaccessible source bodies/links via a lineage traversal. The service may check underlying source liveness under its typed approval lineage; that is not an API read grant.

Confirmation authorizes only this reviewed content, never the source conversation or other memories.

Store references/digests rather than another copy of the text. Confirm accepts only intent ID, stable command key and explicit acknowledgement; it cannot substitute content or target. Editing, changing destination/Bot version, source change or expiration invalidates an uncommitted preview. A preview is not authorization. It can produce at most one approval, even under a different command key. Already committed exact-key receipt replay must remain reachable after a lost response and reauthorize without creating another memory; preview expiry or a later version of the same Bot does not rerun the initial version CAS or narrow the approved scope to the old Bot version. ## 6. Lineage, current-source revocation and MEM-04 compatibility

Every candidate and approved fact retains its canonical output event plus the conservative complete input dependency set; this is causal eligibility, not model-generated citation accuracy. Any bound source edit, tombstone, pending/completed purge, forgotten/upstream revoked memory or invalidated approval immediately excludes the derived body from ordinary list/search/new context and stops publication for Runs that selected it. No privileged historical fallback, source-body substitution, old routing decision, new grant, reindex or exact-key replay can restore eligibility. Newly created memory never joins an already claimed Run.

MEM-04 will add persisted pending-revocation state and an explicit independent-retention decision. Until then, stale lineage is ineligible; approving an edited fact **does not make it independent**. Preserve identifiable ancestor relations so MEM-04 can invalidate every derivative. Its future index rebuild must select only active approved current versions. Keep source/candidate/approved text in explicitly owned content cells; safe audits, job errors, receipts and preview metadata contain IDs/action metadata only. Future purge must cover candidate revisions, approved-fact bodies and any derived index, while retained body-free decision fingerprints prevent recreation. No raw model response, candidate body, provider diagnostics or credentials in audit/error logs.
